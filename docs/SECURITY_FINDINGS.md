# Security Findings Log

Append-only record of security findings, their status and remediation.
Token / secret **values are never written here** — only identifiers, locations and status.
Phase 10.3 of `docs/MASTER_PLAN_EN.md` extends this file with the full attack-scenario results.

| SF-005 | 2026-09-14 | **HIGH** | **13 web API routes are reachable without a session** (found by the Phase 0.3 smoke test `tests/integration/test_smoke_web.py::test_every_api_route_rejects_anonymous_access`). Anonymous responses: `GET /api/patients` → full patient list (200), `GET /api/appointments/today` (200), `GET /api/messages/active` → active relay chats (200), `GET /api/patients/search`, `GET /api/patients/{id}`, `GET /api/appointment/{pid}/{date}/{time}`, `GET /api/events`; mutations: `POST /api/appointments` and `POST /api/messages/send` (send a Telegram message to a patient as the clinic) and `POST /api/treatment-notes/.../send-recommendations` fail only on *missing body fields* (422), `POST /api/calendars/refresh` (200) and `DELETE /api/availability/{id}` (200, deletes a slot). Plus F11's `GET /api/status` and `GET /api/smtp-status`. | **Closed 2026-09-15 (Phase 0.5).** Every `/api/*` router is included with a router-level `require_signed_in` dependency (runs before body validation → 401, never a schema-leaking 422); `/healthz` is the only public endpoint. Regression: `tests/security/test_auth_surface.py` + the smoke test's route sweep (no `xfail` entries remain). |
| SF-006 | 2026-09-15 | **HIGH** | **Multi-tenant IDOR (F6)** confirmed by `tests/security/test_tenant_isolation.py`: a signed-in therapist could read, overwrite, complete, re-diagnose and regenerate points for ANY other therapist's appointment by guessing `patient_id/date/time`, enumerate `/{appointment_id}/debug`, read every patient list / profile / today's schedule, read and delete any relay conversation, send Telegram messages to any patient as the clinic, and delete any local availability slot. | **Closed 2026-09-15 (Phase 0.5).** Object-level scoping everywhere: `resolve_owned_appointment` / `require_appointment_access` in `web/deps.py`; therapist filters in `appointment_repo`, `patient_repo`, `availability_repo`; relay ownership check in `messages.py`; dashboard/patients/search scoped. 403 for an existing row owned by someone else (id path), 404 for triplet lookups (no existence leak). |
| SF-007 | 2026-09-15 | **HIGH** | `POST /api/treatment-notes/{pid}/{date}/{time}/send-recommendations` with `schedule_hours < 24` sent a Telegram message to the `patient_id` taken straight from the URL **without resolving the appointment at all** — any signed-in therapist could message any Telegram user as the clinic. Found because the isolation test's refused request still produced a Telegram API call. | **Closed 2026-09-15.** The appointment is resolved (tenant-scoped) before any branch. Tests now also block real Telegram sends globally (`block_real_telegram` autouse fixture). |
| SF-008 | 2026-09-15 | MEDIUM | Relay conversations are keyed by patient only (`zenflow:relay:*:{patient_id}`); ownership is known only while the `relay:active` key exists. When it lapses, the fallback rule "therapist has an appointment with this patient" lets a therapist who treated the patient earlier read/delete the last 24 h of another therapist's chat. Found by the PR #3 code review (altitude angle). | **Closed 2026-09-16 (Phase 2.4).** History and unread markers are keyed by `(therapist_id, patient_id)` and message routing by `(therapist_id, msg_id)`; the dashboard admits a therapist only to a live session they own or history under their own key. The appointment heuristic is gone; a Redis outage now refuses (404), never grants. The same work found that message ids were keyed globally although Telegram numbers them per chat. Regressions: `tests/security/test_relay_isolation.py`. |
| SF-009 | 2026-09-15 | **HIGH** | `.env.example` carried inline comments after empty values (`SESSION_SECRET=   # …`). python-dotenv reads the comment text **as the value**: a copied template would have signed sessions and encrypted Google tokens with a string committed to the public repo, passing the length/default checks; `ZF_AI_PROVIDER=  # …` refused to boot. Found by the PR #3 code review (three angles independently). | **Closed 2026-09-15.** Template rewritten with comments on their own lines; `tests/security/test_review_regressions.py::test_env_example_parses_clean_and_boots` parses the file with python-dotenv and constructs `Settings` from it. `ZF_AI_PROVIDER=""` now means "use USE_AI". |
| SF-010 | 2026-09-15 | **HIGH** | `send-recommendations` resolved the appointment with the tenant filter and then re-queried it **without** the filter (`ORDER BY created_at DESC`), so with two rows for the same patient/date/time the newer (other therapist's) row was stamped and its contact data used. Found by the PR #3 code review (two angles). | **Closed 2026-09-15.** Re-query is tenant-scoped; regression `test_send_recommendations_uses_the_callers_row_not_a_newer_twin`. |
