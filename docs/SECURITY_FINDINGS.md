| SF-011 | 2026-09-17 | **HIGH** | Stored XSS on the treatment page (plan finding F10): AI lifestyle advice was interpolated into `innerHTML` unescaped, and AI/therapist point codes were spliced into `onclick="quickAddPoint('…')"` / `removePoint('…')` (the old `escHtml` did not escape quotes). | SF-015 | 2026-09-18 | LOW | `GET /auth/login` started Google consent and wrote `next` into the session for an **anonymous** caller: a stranger could begin an OAuth flow against the clinic's client id and plant a redirect target in a fresh session. | SF-017 | 2026-09-24 | MEDIUM | The two patient-facing recommendation messages (`_recommendations_telegram_text`, `_format_recommendations_for_telegram`) were sent with `parse_mode="Markdown"` and interpolated the category and the recommendation `text` into `*{cat}:* {text}` **unescaped**. That `text` is AI-generated advice, and AI output is steerable by whatever a patient typed into the intake (SF-011): unbalanced Markdown (`*`, `_`, `[`, backtick) makes Telegram reject the whole message (HTTP 400), so the patient would receive **no** recommendations, and a crafted `[label](http://evil)` would render a clickable link. Found in the Phase 9.7 output-safety pass. | **Closed 2026-09-24 (9.7).** Both builders escape the dynamic category and text with `telegram.helpers.escape_markdown(…, version=1)`; the static labels stay bold. Regression: `tests/security/test_markdown_injection.py`. (The patient→therapist relay was already immune — the channel is plain-text by default, B2.) |
| SF-018 | 2026-09-24 | **HIGH** | Both Google OAuth flows (Calendar connect `/auth/callback`, and Google registration `/register/google/callback`) generated the `state` parameter but **discarded it** (`url, _ = flow.authorization_url(...)`) and never verified it on the callback. That is the classic OAuth-CSRF / authorization-code-injection hole: an attacker who can deliver a callback URL to the victim's authenticated browser could bind the victim's session to the **attacker's** Google account (or the attacker's session to the victim's code), with no cross-check. Found by the Phase 10 (A12) offensive-testing pass. | **Closed 2026-09-24 (10.2).** Both flows now stash the library-generated `state` in the session when the flow starts (`_OAUTH_STATE_KEY`) and the callbacks refuse a code whose `state` does not match, single-use and compared with `secrets.compare_digest` (`web/deps._verify_oauth_state`). A forged or missing state never reaches the token exchange. Regression: `tests/security/test_oauth_state.py`; the existing `test_google_oauth_next.py` round-trips now carry the state. |
| SF-016 | 2026-09-23 | LOW | The Content-Security-Policy (9.4, ADR-37) ships **report-only**, not enforcing, because the dashboard pages still carry inline `on*=` event handlers, inline `<script>` blocks and inline `style=` attributes, and load Google Fonts + FullCalendar from external origins. A report-only policy warns but does not block, so an injected inline script is *not yet* stopped by the CSP on these pages (server-side escaping and the nonce on legitimate scripts still apply). Only the treatment page (Phase 4.1) is already free of inline handlers/scripts. | **Open — tightening tracked.** Path to enforce (`ZF_CSP_ENFORCE=1`, no code change): (a) replace inline `on*=` handlers with delegated `data-action` handlers as `static/js/treatment/events.js` already does; (b) move inline `style=` attributes and `<style>` blocks to classes so `style-src` can drop `'unsafe-inline'`; (c) self-host the fonts and FullCalendar under `/static` to drop the external origins. The per-request script nonce is already wired on every inline/CDN script, so no plumbing remains. |
